## Headline: itermon now works in any terminal, and over SSH on Linux

itermon spoke only iTerm2's AppleScript automation interface. That meant macOS + iTerm2, full
stop. This release adds a **tmux backend**, so itermon now works inside Ghostty, Warp, Alacritty,
WezTerm, Terminal.app, VS Code's integrated terminal — **and over SSH on a Linux box**, which is
where a lot of the "babysit a long-running AI agent" use case actually lives.

**The honest cost, stated plainly:** for any terminal other than iTerm2 on macOS, your work has
to already be running *inside a tmux session*. itermon talks to tmux, not to the terminal window
itself, on every backend except iTerm2. If you're on macOS with iTerm2, nothing about your
workflow changes — no tmux involved, same as always.

**What did NOT get the cross-platform treatment this release:** the local web admin
(`iterm-admin`) and the cron scheduler stay **macOS + iTerm2 only**. The README says so; these
notes are not going to imply otherwise.

### How backend selection works
- New flag: `--backend {auto,iterm2,tmux}` on `list`, `send`, `read`, `watch`.
- New env var: `ITERMON_BACKEND` (`iterm2` | `tmux`) — how the MCP server and any scripted
  caller pick a backend without a code change.
- Default (`auto`): **macOS → iTerm2, everything else → tmux.**
- **Deliberate ruling, not a bug:** `auto` does **not** switch to tmux on macOS just because
  `$TMUX` is set (i.e. you're already inside a tmux pane inside iTerm2). Every macOS user keeps
  getting iTerm2 output on upgrade, unconditionally. If you want the tmux backend on macOS, ask
  for it explicitly: `--backend tmux` or `ITERMON_BACKEND=tmux`. This was a conscious call to
  avoid an upgrade silently changing what `list`/`send`/`read` return for existing users.
- Unknown backend name fails closed with the valid options listed — never a silent fallback.

### New: `iterm-ctl backends`
Prints both backends, whether each is available on this machine, which one `auto` would pick
here, and the full capability table (stable ids, job column source, cwd, scrollback, OS
permission requirement, cross-platform). No need to read the README to find out what you get.

### Identity / targeting
`resolve_targets` now also accepts an **exact match on index or id** as a selector, so tmux pane
addresses (`work:2.0`) and bare pane ids (`%3`) work the way tmux users already expect. Every
existing iTerm2 selector (`id:`, `tty:`, `name:`, bare index, `--all`) is unchanged — this is a
strict addition, not a replacement.

## Packaging: `os: ["darwin"]` removed

`npm install itermon` used to hard-fail on Linux with `EBADPLATFORM` — the `os` field in
`package.json` enforced it. That's gone. **Read this precisely:** it means you can now *install*
itermon on Linux. It does not mean every feature works there — see the platform table above
(web admin + cron scheduler are still macOS + iTerm2 only). Removing a restriction can't break an
existing macOS install; it only widens who can install the package. Not a breaking change.

Also additive this release: an `itermon` bin alias next to the existing `iterm-ctl` (which is not
going anywhere — permanently supported).

## Also shipping in 1.3.0: MCP unknown-tool error shape (not new work, but newly released)

This landed on `develop` on 2026-07-29 (`bb119d8`) and has been sitting there unreleased since.
It rides out with 1.3.0 because it was already accepted and there's no reason to hold it
further, but it is a real behavior change on one path and I'm naming it per standing instruction:

**Before:** an MCP `tools/call` naming a tool that doesn't exist raised a raw JSON-RPC `-32603`
transport-level error.
**After:** it returns a normal **tool result** with `isError: true` —
`{"content": [{"type": "text", "text": "Unknown tool: '<name>'. Available tools: <list>"}],
"isError": true}` — the same shape as any other tool execution failure, so an MCP
client/model gets a readable, recoverable error instead of a transport fault, and the message now
names the available tools (the old raw RPC error didn't).

Judged **patch-level**, not breaking: it only changes the *shape* of an interaction that was
already failing every time (no successful call behaves differently), and any MCP client that
correctly reads `isError` on a tool result — which is the protocol's own error-signaling
mechanism — handles it the same way it handles every other tool error. A client that specifically
pattern-matched on the old raw `-32603` for this one case would need to adjust; that is a narrow
enough edge that I agree with the PM's original patch-level call, but you should know it exists.

## Why minor, not major (1.3.0, not 2.0.0)

- New backend, new flag, new env var, new subcommand, widened install target — all additive.
- Nothing removed. No existing function signature changed.
- The macOS/iTerm2 path is **verified byte-identical**: `iterm_mcp.py` and `iterm_web.py` have a
  0-line diff from this work; the generated AppleScript output was diffed against the pre-change
  output and matches exactly.
- The one named behavior change (MCP unknown-tool shape) is judged patch-level on its own merits
  (see above) and was already ruled on at merge time, independent of this release's version call.

If anyone downstream disagrees that the unknown-tool shape is patch-level, that's a legitimate
challenge — flag it back to the PM (Messi), who made and owns that call.

## Rollback note

No breaking change ships in 1.3.0, so rollback pressure should be low. If a defect surfaces
after publish:
- **Do not `npm unpublish`** — company/npm policy: it can break installs already pinned to
  1.3.0 and npm restricts it after 72 hours anyway.
- Standard path: `npm deprecate itermon@1.3.0 "<reason>"` to warn installers, then ship a
  1.3.1 patch fixing the defect.
- If the defect is specifically in the tmux backend and the iTerm2 path is unaffected (expected,
  given the byte-identical verification above), a user can route around it immediately with
  `ITERMON_BACKEND=iterm2` (macOS) — no waiting for a patch. Worth saying in the deprecation
  message if this is the failure mode.
- If the MCP unknown-tool shape change turns out to surprise someone despite the patch-level
  call, that's a docs/communication fix (call it out more loudly), not a code revert — the new
  shape is strictly more correct protocol behavior.
