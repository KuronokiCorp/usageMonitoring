## Headline: closes a live remote-code-execution hole in the web admin (BACKLOG #12)

**itermon@1.3.0, currently live on npm, is vulnerable.** Before this fix, `iterm_web.py`
(`iterm-admin`, the local web admin) served `/api/send` and every other `/api/*` route with
**no `Origin` check, no `Host` check, and no authentication**. Any web page a user simply
*visited* — no interaction beyond loading the page — could POST a `text/plain`-labelled
request (a CORS "simple request": no preflight, no browser warning) and have arbitrary text
typed and Entered into **every one of the user's terminal sessions**, including any Claude
Code / AI-agent panes with live tool permissions. This is arbitrary command execution via a
drive-by webpage, not a theoretical weakness.

**If you run `itermon`'s web admin (`iterm-admin`), upgrade to 1.4.0 immediately.** If you only
use the CLI (`iterm-ctl`/`itermon`) or the MCP server, you were never exposed by this specific
hole — it is `iterm_web.py`-only.

### The fix: an `Origin` + `Host` allowlist, both fail-closed
- Checked on **every** request, on **every** HTTP verb, **before** the body is read and
  **before** any route dispatch — not something a future handler can accidentally bypass.
- `Host` header not on the allowlist → rejected (closes DNS rebinding too).
- `Origin` header present but not allowlisted, or `Origin: null` → rejected,
  `403 {"error":"forbidden"}`.
- Allowlist is always derived from the address the server is actually bound to — never a
  hard-coded port, so `--bind`/custom-port setups are covered automatically.
- **The one asymmetry the whole fix rests on, stated precisely:** a request with **no**
  `Origin` header at all is allowed. Browsers *always* attach `Origin` on a cross-origin
  request of this shape; `curl`/`wget`/`requests`/shell scripts never send one. This is why
  `curl -d '...' localhost:8765/api/send` keeps working unchanged and no token/auth scheme
  had to be introduced.
- New opt-in flag: `--allow-origin ORIGIN` (repeatable) for a LAN address browsed by
  hostname, or a future browser extension (`chrome-extension://<id>`) — validated at
  startup, refuses `*` and anything with a path component.
- Rejected-request logging is rate-limited (first rejection logged immediately, then at most
  once per 60s with a suppressed-count) so a drive-by attempt can't be turned into a disk-fill
  attack on the Activity log (BACKLOG #7/#11 lesson, applied here defensively).

### Honest limits — read this, don't just read the headline
- **This does not authenticate anything.** Any *other* local process on the same machine can
  still call the API with no `Origin` header and be obeyed, same as before. This closes the
  browser drive-by vector specifically, not "all unauthenticated local access."
- An XSS bug in the admin page itself would bypass this fix entirely (same-origin requests
  are, correctly, allowed).
- `Content-Type` is deliberately **not** validated — doing so would also break
  `curl -d '...'`, which sends no `Content-Type` browsers would recognize as "simple."

## Also in 1.4.0: the stable-job-targets / 0-match-as-failure line (BACKLOG #6)

Landed on `develop` the day before the RCE fix, riding the same unreleased line:

- **`index:` selector.** `iterm-ctl send index:2.1.1 "..."` used to silently match nothing
  (fell through every branch to the bare-substring fallback). It's now an explicit selector
  alongside `id:`/`tty:`/`name:`/bare-index — same exact-match semantics, fully additive.
- **A 0-match scheduled send is now a visible failure, not a silent success.** This was the
  root cause of a 20-day-silent broken job (BACKLOG #6): a rotted target used to log and
  report exactly like a legitimate empty send. It now logs `kind: "error"` and returns a
  distinct status (`"MATCHED 0 SESSIONS — not delivered"` from the scheduler; a new
  `"matched": 0` field from `/api/send`, with the existing `{"sent": N}` key and `200` status
  kept byte-identical for scripts that depend on them). A 1-or-more-match send is unchanged.
- **The admin UI stopped minting session-UUID (`id:`) targets for new scheduled jobs** — the
  actual root cause of the rot. New jobs now save `index:<n>` (survives session recreation in
  the same pane position). Manual-send stays on `id:` on purpose (no time window to rot in).
  Existing jobs already saved as `id:` are untouched and keep working.

## Why minor, not major (1.4.0, not 2.0.0)

- The security fix is a **new server-side restriction on who may call `/api/send`**, not a
  change to the request/response contract for a legitimate caller. Every caller that never
  sent a (bad) `Origin` header — every non-browser client that exists today — sees zero
  behavior change.
- `/api/send`'s existing `{"sent": N}` response key and `200` status are preserved exactly on
  both the happy path and the new 0-match path; the 0-match case only *adds* a `"matched"`
  field, it doesn't remove or repurpose anything.
- `resolve_targets`'s existing selector set (`id:`/`tty:`/`name:`/bare-index/`--all`) is
  unchanged; `index:` is additive.
- Nothing was removed. No existing function signature or CLI flag changed shape.
- This is a security **hardening**, and per this product's own semver discipline, breaking
  changes always land as major — this one doesn't break anything that was working correctly
  and unauthenticated-by-design use of the API was never a documented, supported contract.

## Rollback note

No breaking change ships in 1.4.0. If a defect surfaces after publish:
- **Do not `npm unpublish`** — company/npm policy; can break installs pinned to 1.4.0, and npm
  restricts it after 72 hours regardless.
- Standard path: `npm deprecate itermon@1.4.0 "<reason>"`, then ship a 1.4.1 patch.
- **If the Origin/Host guard itself is the defect** (e.g. a legitimate same-origin caller gets
  wrongly rejected): the immediate user-side workaround is `--allow-origin` naming the exact
  origin that needs to work, no code change required while a patch is prepared. Do **not**
  suggest disabling the guard entirely as a workaround — that reopens BACKLOG #12 and the
  vulnerability is what this release exists to close.
- If the stable-job-targets / 0-match change is the defect: it only changes logging/status
  strings and an additive JSON field; reverting the two commits (`3eaa404`, `4e9f988`) cleanly
  is low-risk if needed, independent of the security fix.

plain fast-forward-shaped merge. **I checked with `git merge-tree` (a dry-run, no working-tree

1. `git -C <main-worktree> merge --no-ff release/1.4.0-prep -m "Release itermon v1.4.0: promote develop to main"`
   — merge **this prepared branch** (develop's tip + the version bump/CHANGELOG/spec-recovery
